# Lessons

Pitfalls and decisions to check before making a change. Each entry is a rule: what to watch for and why, not the story of what happened. The tag says where it came from:

- `bug`: found or fixed in code.
- `correction`: the owner corrected an assumption or redirected the approach.
- `design`: a product or UI decision the owner made that later changes must keep.

The rule applies whatever its origin. The lessons live in area files under [`lessons/`](lessons/). This page says which to read and indexes them all. How and when to add one is in [`AGENTS.md`](../AGENTS.md) under "Recording lessons".

## Which files to read

Read [`lessons/general.md`](lessons/general.md) for any change. Also read the files for what the change touches:

| If the change touches... | Read |
| --- | --- |
| `apps/server/` (routes, database, engine, agents, assistant, model calls, storage) | [`lessons/server.md`](lessons/server.md) |
| `apps/web/` (pages, top bar, menus, styles, store) | [`lessons/web.md`](lessons/web.md) |
| `scripts/demo/`, demo scenarios, saved copies | [`lessons/demo.md`](lessons/demo.md) |
| `Dockerfile`, `deploy/cloudflare/`, dependencies, Node version | [`lessons/deployment.md`](lessons/deployment.md) |

A change across areas reads each matching file. When a slug is cited somewhere, find it in the index below.

Lessons marked **(check)**, **(test)** or **(code)** in the index are enforced by `scripts/checks/lesson-checks.mjs`, a test script or a guard in the code, so you don't need to check them by hand. `npm run check:lessons` runs the checks and fails if this index is stale.

## Adding an entry

Add it to the area file that fits, under the closest `##` section, then run `npm run lessons` to rebuild the index.

```
### short-kebab-case-slug `bug` | `correction` | `design`
The rule, stated as a pattern to check for. **Why:** the cause, if not obvious. **Applies to:** where it matters, if not obvious.
**Enforced by:** check <name> | test <script> | code <file> | none - <why it needs judgement>
```
