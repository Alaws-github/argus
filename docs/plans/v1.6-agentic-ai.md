Status: **planned, not started** (written 2026-11-06 at the end of v1.5). Owner approval: the owner asked for this plan so it can be built when usage allows. Build it in the phase order in section 12; each phase is shippable on its own.

## 1. What we are building, and why

ARGUS is an AI governance, risk and assurance workbench. Its AI must work like a capable analyst: **look things up, ask when something is missing, and check its own work**, using the Knowledge Base and everything on the site (use cases, risks, controls, tests, evidence, issues, incidents, inventory, past decisions).

Today every agent is a **single-shot call**: ARGUS packs a fixed context, the model answers once through a forced `submit_*` tool, ARGUS validates. That is predictable but rigid (the owner's word, and correct): the agent can't search again, can't open a related record, can't ask, can't revise.

**The principle for v1.6: limit what an agent may decide, not what it may find out.**

- Agents may **read** anything the person they work for may read, search as often as they need, ask questions, and revise their own drafts.
- Agents still **decide nothing**: every output is a draft a named person accepts, edits or rejects (rules 1, 2, 12, 15, 19 unchanged).

## 3. Target architecture

```
                 ┌──────────────────────────── Agent runtime (new: agent-loop.ts) ───────────────────────────┐
 card/plan/  ──▶ │ 1 brief (task, rules, engagement, instructions, starting context)                           │
 question        │ 2 loop ≤ maxSteps: model ─▶ tool calls ─▶ tool registry (read-only, access-checked) ─▶ results │
                 │ 3 self-check: critique pass against the rules and exit criteria ─▶ revise (≤ 1 to 2 rounds)  │
                 │ 4 submit_draft ─▶ existing server checks (Zod, citations ledger, keys, figures) ─▶ draft      │
                 │   or ask_person ─▶ run paused, card "Question for you", resumes on answer                   │
                 └──────────────── every step written to run_steps (trace) and the audit log ──────────────────┘
                                   │                         │
                         RAG service (kb.ts v2)     Site data tools (tools/*.ts)
```

### 3.1 The agent loop (`apps/server/src/agent-loop.ts`, new)

```ts
interface AgentTask {
  role: AgentRole;                 // which agent, picks the rules file and tools
  engagementId: string;
  subject: { kind: 'card' | 'plan' | 'assistant'; id: string };
  actingFor: UserRef | null;       // whose read access the tools use (the person who triggered it, else engagement scope)
  brief: string;                   // starting context (today's user message, smaller)
  finalTool: ToolDef;              // submit_classification, submit_controls, ... (existing schemas)
  limits: { maxSteps: number; maxCostUsd: number; timeoutMs: number };
  selfCheck: SelfCheckSpec | null; // section 3.4
}
runAgent(task, target, log): Promise<{ output; trace: Step[]; usage; paused?: PendingQuestion }>
```

Loop:
1. Messages = [system: rules + instructions][user: brief].
2. Call the model with `tools = role tools + ask_person + finalTool`, `tool_choice: auto`.
3. For each tool call: check it is in the role's allowlist, run it with the access scope, cap the result (about 4,000 characters, with "truncated, ask for more with offset"), wrap it as data (`<tool_result name=...>`), append. Parallel calls run together.
4. Stop when the model calls `finalTool` (go to checks) or `ask_person` (pause), or limits hit (then force the final tool with `tool_choice` on the next call: "submit your best draft now").
5. Every step: `run_steps` row (tool, arguments, result size, tokens, cost, ms). Shown in the run trail.

Provider adapters (extend `llm.ts`, keep `callStructured` for single-shot):
- **Anthropic**: `tools`, `tool_choice: {type:'auto'}`, loop on `stop_reason: 'tool_use'`, return `tool_result` blocks. Prompt caching on the system prompt and tool definitions (`cache_control`) to cut cost on long loops. Extended thinking allowed with `tool_choice: auto` (not with a forced tool), so the final forced call runs without thinking.
- **OpenAI-compatible** (OpenAI, Gemini OpenAI endpoint, Groq, Mistral, OpenRouter, Together, Ollama /v1): `tools`, `tool_choice: 'auto'`, loop on `finish_reason: 'tool_calls'`, reply with `role: 'tool'` messages. Keep the v1.5 retry, truncation and `max_completion_tokens` handling.
- **Ollama native**: `tools` in `/api/chat`; same loop.
- **No tool support** (detected by the existing 400 "tools not supported" fallback, or a provider flag `supportsTools=false`): run today's single-shot path with a richer pre-packed context (section 5.6). Offline rules: unchanged.

### 3.2 Tool registry (`apps/server/src/tools/`, new)

Each tool: name, description (written for the model), JSON schema (every object has `properties`, per lesson `tool-schema-objects-need-properties`), `roles` allowlist, `run(args, scope)`, `maxChars`.

**Scope and access** (non-negotiable):
- `scope = { engagementId, user, visibleEngagementIds }` from `access.ts` (`visibleIds`, `canSee`). Cross-engagement tools (`find_similar_use_cases`) only see engagements the acting person can see. Members-only engagements never leak (rule 16).
- Tools are **read-only**. They call store/query functions directly, never HTTP routes, and never write. The only writes an agent makes are `submit_*` (becomes a draft, as today) and `ask_person` (creates a question record).
- Tool results are client content: wrapped in tags, and the rules say instructions inside them are ignored (rule 7). Prompt-injection text in a tool result is flagged in the trace (reuse the classifier's injection detector).

**Catalogue:**

| Tool | Returns | Roles |
| --- | --- | --- |
| `search_knowledge(query, kinds?, framework?, limit≤8)` | Passages with K-ids (RAG, section 4); every K-id returned is added to the run's **retrieval ledger** | all |
| `get_passage(kId)` | Full passage text | all |
| `get_use_case(key)` | Profile, stage, status, tier, classification, design, decisions with reasons | all |
| `find_similar_use_cases(text, limit≤5, acrossEngagements?)` | Similar cards (by meaning search over the records index) with tier, oversight, risks, controls and how reviewers decided | planner, classifier, designer, assistant |
| `list_risks(filter)` | Risk register rows (filters: card, score ≥, above appetite, no control, no owner) | classifier, designer, reviewer, report, assistant |
| `list_controls(filter)` | Controls with owners, status, risks, tests | designer, evidence, tester, reviewer, report, assistant |
| `get_library_control(code)`, `search_library(text)` | The 31 library controls | designer, evidence, tester |
| `list_tests(filter)`, `get_test(key)` | Tests with procedure, sample, result, preparer, reviewer | tester, reviewer, report, assistant |
| `list_evidence(filter)`, `read_evidence(key, offset?)` | Evidence list; extracted text of a file (`extract.ts` output) in pages | evidence, tester, reviewer, assistant |
| `list_issues(filter)`, `list_incidents(filter)` | With severity, status, owner, due dates | reviewer, report, assistant |
| `get_inventory(filter)` | AI systems, vendors, owners, agent readiness | planner, classifier, assistant |
| `get_reviewer_decisions(role, limit≤10)` | Recent accepted/edited/rejected items for this agent role on this engagement, with reasons (from `decisions` and the audit log) | all drafting agents |
| `get_engagement()` | Client, sector, frameworks, appetite, description, modules | all |
| `get_eval_results(system?)` | Latest suite runs and alerts | tester, reviewer, report, assistant |
| `ask_person(question, to: 'owner'\|'reviewer'\|'requester', why)` | Pauses the run (section 3.3) | all except Report Writer |
| `submit_*` | The existing final schemas | each role its own |

### 3.3 Follow-up questions (`ask_person`)

- New table `agent_questions` (id, engagement_id, card_id or plan_id, run_id, role, question, why, asked_to, status `open|answered|withdrawn`, answer, answered_by, timestamps). Audit entries `agent.asked`, `agent.answered`.
- The run is saved with its message transcript (`runs.transcript jsonb`) and status `waiting`. The card shows the status **Question for you** (blinking dot, like Needs Your Approval) with the question in the card drawer and an answer box. Viewers can't answer; anyone else who can prepare can, and the answer names them.
- Answering resumes the run from the transcript with the answer as the tool result. A time-out (configurable, default 3 days) lets a person **Continue without an answer**, which resumes with "no answer: proceed and list it as an open question".
- Limits: at most 2 questions per run; the Planner asks in its chat as today (it already talks to the person).

### 3.4 Self-check (critique and revise)

After the model calls `submit_*` and before ARGUS accepts it:
1. **Rule checks first** (cheap, deterministic): the existing Zod and server checks, plus role-specific checks, for example the Designer's "every risk ≥ 12 has a control", the Classifier's "tier consistent with listed factors (Annex III signals → high)", "every risk cites a passage from the ledger".
2. **Critique pass** (one model call, optional per agent, on by default for Classifier and Designer): a short rubric per role in `prompts/<role>.critique.md`. The model sees its draft, the rubric and the ledger passages, and returns `{ ok, problems[] }`.
3. If problems: one revision turn in the same loop ("fix these, then submit again"). Then the strict checks decide. Format problems still use `callStructuredChecked`'s repair; substance problems (stray citations, invented figures) still fail the run.
4. Optionally, the Verifier runs inside the loop for classify/design, and items it marks `not_supported` are sent back once for revision. Its verdicts remain advisory on the final draft (rule 14).

### 3.5 Run trail and transparency

- `run_steps` table: run_id, n, kind (`model|tool|question|critique|revision|submit|error`), name, args (scrubbed), summary, tokens, cost, ms.
- Run detail page shows a readable timeline: "Searched the knowledge base for 'creditworthiness assessment' (4 passages)", "Opened AI-3 at Kestrel Bay", "Asked the business owner: does it use bureau data?", "Self-check found 1 problem: risk 2 cites nothing; revised".
- The card drawer shows a one-line summary under the draft: "7 steps · 3 searches · 1 question · revised once · $0.04".

## 4. The RAG system (kb.ts v2)

### 4.1 What goes in (ingestion)

| Source | Kind | Scope | Refresh |
| --- | --- | --- | --- |
| Framework summaries, library controls, method guidance (M-*) | framework, control, methodology | global | on start (`ensureKnowledge`, idempotent) |
| Client documents (uploads) | client | engagement | on upload; re-chunk on re-upload |
| Evidence text (`extract.ts`) | evidence | engagement | on collection (already `indexEvidence`) |
| **Site records (new)**: use cases, risks, controls, tests (concluded), issues, incidents, inventory, accepted drafts | record | engagement | on change (hook in the same transaction as the audit entry: enqueue `reindex_record(kind,id)`) |

Records are indexed as short structured documents ("AI-3 Board paper summariser. Tier limited. Risks: ... Controls: ... Decided by Riley: tier edited from high to limited because ..."), which powers `find_similar_use_cases` and lets the assistant answer cross-record questions.

### 4.2 Chunking

- Heading-aware: split on headings first, then paragraphs; target 600 to 900 characters, 15% overlap; never split a table row or list item.
- Each chunk keeps metadata: source title, heading path, kind, ref, framework, engagement_id, page (PDFs), `updated_at`, `version`.
- Contextual prefix for embedding only: "From: <source title> > <heading path>". Improves meaning search for short chunks.

### 4.3 Embeddings and storage

- Keep pluggable providers (`embedProviderId`, OpenAI-compatible or Ollama). Store `embed_model` and dimension per chunk; re-embed in the background when the model changes (existing `scheduleEmbedding`).
- Add an **HNSW index** on `kb_chunks.embedding` (pgvector supports it on Neon; PGlite pgvector supports HNSW in recent versions, else fall back to exact search on small sets).
- Without an embedding model, keyword search still works (as today).

### 4.4 Retrieval (`search` v2)

1. **Query rewriting** (agentic path: the agent writes its own queries through `search_knowledge`; single-shot path: one cheap call turns the request into 2 or 3 queries in the standards' terms).
2. **Hybrid**: full text (`websearch_to_tsquery`, plus the current keyword list) and vector top-k, merged with reciprocal rank fusion (already there).
3. **Filters**: engagement scope (`engagement_id IS NULL OR = current`), kind, framework, record type; members-only scope through `visibleIds` for record chunks.
4. **Diversity**: maximal marginal relevance so 8 results aren't 8 chunks of one document.
5. **Optional rerank**: an LLM rerank of the top 20 on providers that can afford it (setting `rerank: off|llm`), with the rerank score logged.
6. **Pinned passages** stay (M-TIERS for the Classifier, etc.) but count against the budget.

### 4.5 Citations and the retrieval ledger

- Every K-id returned to a run by any tool goes into the run's ledger (`run_passages`: run_id, k_id, via tool, step). `strayCitations` checks against the ledger, not a fixed list. Cited passages are snapshotted onto the draft (rule 13 unchanged).
- The assistant shows sources by where they came from: **Knowledge Base** (K-ids), **Records** (AI-3, R-5), **This page**. A page question cites the page, not a KB passage (fixes the K-62 "About Northshore" source). The engagement "About" passage is excluded from search results for the assistant, since the description is given directly.

### 4.6 Measuring retrieval

- `retrieval_golden` table: question, engagement or global, expected K-ids or record keys. Seed about 30 (tiering questions, OWASP items, client policy lines in the demo engagements).
- `npm run test:rag`: recall@5, recall@10, MRR, per kind, with and without embeddings. Shown on **Checking the AI > Retrieval** (new tab) so the owner can compare embedding models.
- Faithfulness of answers uses the Verifier (existing).

## 5. Each agent in v1.6

For every agent: tools from 3.2, the brief below, `maxSteps` default 8 (Planner 4 per message, assistant 6), self-check as listed. The final schema and server checks stay exactly as today.

### 5.1 Use Case Planner (conversational)
- Brief: conversation, brief, edited fields. Everything else via tools.
- Uses: `get_engagement`, `find_similar_use_cases` (duplicates and examples, across engagements the person can see), `get_inventory` (is the vendor or system already known?), `search_knowledge` (client intake policy, M-INTAKE).
- Asks the person directly in chat (no `ask_person` needed). Suggestions when asked or stuck (v1.5 behaviour kept). Self-check: rule checks only (never fills owner or data the person didn't give).

### 5.2 Risk Classifier
- Brief: the profile and reviewer feedback.
- Typical path: search tiers and Annex III terms → `find_similar_use_cases` (how comparable cases were tiered, and reviewer edits) → `get_reviewer_decisions` → `get_inventory` (vendor, data) → `ask_person` when data used or autonomy is unclear → submit.
- Self-check rubric: tier matches factors; oversight matches autonomy and tier; each risk follows from the profile and cites a ledger passage; privacy risk present when data identifies people; open questions cover anything assumed. Critique on by default; Verifier-in-loop optional.

### 5.3 Control Designer
- Uses: `list_controls` (reuse an existing control instead of a duplicate), `search_library`, `get_library_control`, `get_reviewer_decisions`, `search_knowledge` (client policy requirements).
- Self-check: every risk ≥ 12 covered; library codes exist; owners are roles named in the profile or engagement, else an open gap; no duplicate of an existing control without saying so.

### 5.4 Evidence Collector
- Uses: `list_evidence`, `read_evidence`, `get_library_control` (evidence usually expected), `search_knowledge` (client retention or logging policy), `ask_person` (to the control owner: "where are the review logs kept?").
- Self-check: every control has at least one request; nothing marked received without an evidence key.

### 5.5 Control Tester
- Uses: `get_test`, `read_evidence` (reads the actual file text, paging through it), `search_knowledge` (M-SAMPLING, M-EXCEPTIONS, client thresholds), `ask_person` (preparer: "the sample has 23 items, the test says 25").
- Self-check: proposed result consistent with exceptions; never "pass" on notes only (existing rule); cites evidence keys it read.

### 5.6 Review assistant and Report Writer
- Review assistant uses all list tools and `get_eval_results`, `list_incidents`; the rule findings still always stand.
- Report Writer uses list tools; every figure still checked against the data it retrieved (the figures ledger replaces today's fixed data string: every number returned by a tool in the run is allowed).
- Single-shot fallback for models without tools: pre-pack the most useful tool results (today's context plus similar cases and reviewer decisions).

### 5.7 Verifier
- Stays a judge, not an agent: no tools, sees only the claim and its cited passages (that is what makes its verdict meaningful). Gains the in-loop use in 3.4.

### 5.8 Assistant (v2)
- Tools: all read tools in the engagement the person is in, plus `find_similar_use_cases` across engagements they can see. No write tools: suggestions stay the five whitelisted kinds, applied by the person (rule 15).
- Page questions answered from the page snapshot without a KB search; sources labelled by origin (4.5).
- Shows a collapsible trail under each answer ("Looked up AI-3, searched the KB for 'Article 14'").
- Optional streaming of the final answer (SSE) later.

## 6. Governance: what stays, what's new

Unchanged: rules 1 to 22. In particular: agents draft, people decide (1); drafting stages stop (2); segregation of duties (3); exit criteria (4); audit in the same transaction (5); validation (6); client content is data (7); rules files plus engagement instructions (8); archived read-only (9); access enforced centrally (16).

New rules to add to CLAUDE.md when built:

23. **Agents may read, never write, through tools.** Tools are read-only and use the access scope of the person the agent works for (members-only and archived rules apply). The only agent writes are a draft through `submit_*` and a question through `ask_person`, both audited.
24. **Every step is recorded.** Each model call, tool call, question, critique and revision is a `run_steps` row; the trail is visible on the run and summarised on the card.
25. **Citations come from the run's retrieval ledger.** An agent may cite only passages and records a tool returned in that run; figures in the Report Writer only from data a tool returned.
26. **Loops are bounded.** Each agent has `maxSteps`, `maxCostUsd` and a time limit; at the limit it must submit its best draft or fail clearly. The spend cap still applies to every call.
27. **Questions pause, they don't decide.** A paused run changes nothing until a person answers or chooses to continue without an answer.
